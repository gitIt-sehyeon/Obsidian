# Privileged Programs 정리

## 1. Two-Tier Approach (이중 계층 접근 방식)

### 핵심 문제

OS가 모든 **세밀한(fine-grained) 접근 제어**를 직접 구현하면 OS가 지나치게 복잡해진다.

### 해결책: 2계층 구조

|계층|역할|
|---|---|
|**OS (1계층)**|범용적인 접근 제어만 담당 (시스템 콜 수준)|
|**특권 프로그램 (2계층)**|세밀한 접근 제어 로직을 직접 구현|

```
일반 사용자
    ↓
Privileged Program  ← "정말 허용해도 되나?" 검증
    ↓
보호된 자원 (예: /etc/shadow)
```

### 구체적 예시: `passwd` 프로그램

```bash
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 41284 Sep 12 2012 /usr/bin/passwd
```

- **setuid 비트(`s`)** 설정 → 실행 시 root 권한으로 동작
- 내부적으로 세밀한 로직(현재 비밀번호 확인, 정책 검사 등)을 수행한 뒤 `/etc/shadow` 수정

## 2. Privileged Program이란?

일반 사용자는 접근할 수 없는 **보호된 자원(Protected Resource)** 에 접근할 수 있는 특별한 권한을 가진 프로그램.

**OS 대신 세밀한 접근 제어 로직을 구현하는 중간 관리자 역할**을 한다.

---

## 3. Types of Privileged Programs

### Daemon (데몬)

- 백그라운드에서 **지속적으로 실행**되는 프로그램
- **root 또는 다른 특권 사용자** 권한으로 실행
- 이름 끝에 관례적으로 `d`가 붙음
- 예시: `sshd`, `httpd`, `cron`, `syslogd`

### Set-UID Program

- UNIX 시스템에서 널리 사용
- **특수 비트(setuid bit)** 로 표시된 프로그램
- 실행 시 **파일 소유자의 권한**으로 동작
- 예시: `passwd`, `ping`

|구분|Daemon|Set-UID Program|
|---|---|---|
|실행 방식|항상 백그라운드 상주|필요할 때 일시 실행|
|권한 부여 방법|시작부터 root로 실행|특수 비트로 실행 중 권한 상승|
|대표 예시|`sshd`, `httpd`|`passwd`, `ping`|

## 4. RUID vs EUID

||의미|역할|
|---|---|---|
|**RUID** (Real UID)|실제 로그인한 사용자|"나는 누구인가"|
|**EUID** (Effective UID)|현재 권한 판단 기준|"나는 지금 무슨 권한인가"|

OS는 접근 제어 판단 시 **EUID**를 본다.

### Set-UID 실행 전후 비교

일반 사용자(uid=1000, bob)가 `passwd` 실행 시:

```
일반 프로그램 실행 시:
  RUID = 1000 (bob)
  EUID = 1000 (bob)   ← 동일

Set-UID 프로그램(passwd) 실행 시:
  RUID = 1000 (bob)   ← 그대로 (진짜 나는 bob)
  EUID = 0    (root)  ← 승격! (파일 소유자 권한)
```

- **RUID**: 바뀌지 않음 → "원래 누가 실행했는지" 추적 가능
- **EUID**: 파일 소유자(root)로 승격 → 실제 권한 행사는 root로

## 5. 파일 권한 읽기

```
-rwxr-xr-x 1 root seed 46764 mycat
  ↑↑↑ ↑↑↑ ↑↑↑
  │   │   └── others 권한
  │   └─────── group 권한
  └─────────── owner 권한
```

|필드|값|의미|
|---|---|---|
|**소유자 (Owner)**|`root`|파일을 소유한 사용자|
|**그룹 (Group)**|`seed`|파일이 속한 그룹|

### 그룹이란?

사용자를 **묶어서 관리**하기 위한 단위. 파일 권한을 개인마다 따로 설정하지 않고 그룹 단위로 부여 가능.

> 리눅스에서는 사용자를 만들면 **보통 같은 이름의 그룹이 자동 생성**된다.

## 6. setuid 비트 설정 방법

### 실행 권한(x) vs setuid(s) 차이

|비트|의미|
|---|---|
|`x`|이 파일을 **실행할 수 있다**|
|`s` (setuid)|실행 시 **소유자 권한으로 EUID가 승격된다**|

`x`는 실행 가능 여부, **EUID 승격은 `s` 비트만이 일으킨다.**

### chmod로 setuid 설정

```bash
chmod 4755 mycat   # setuid 설정 → -rwsr-xr-x
chmod 0755 mycat   # setuid 해제 → -rwxr-xr-x
```

### 숫자 권한 해석

```
4  7  5  5
↑  ↑  ↑  ↑
특수비트  owner  group  others
```

|특수비트 값|의미|
|---|---|
|**4**|setuid|
|**2**|setgid|
|**1**|sticky bit|
|**0**|없음|

## 7. Attack on Superman (특권 프로그램의 취약점)

> "사용자가 코드에 짜여진 것만 할 것이라고 가정하면 안 된다"

개발자의 코딩 실수가 있으면, 공격자가 의도하지 않은 동작을 유발할 수 있다.

### 비유

|비유|실제 의미|
|---|---|
|슈퍼맨|Set-UID 특권 프로그램|
|은행(금괴)|보호된 자원 (`/etc/shadow` 등)|
|경로 1|개발자가 의도한 정상 흐름|
|경로 2|코딩 취약점을 통한 우회 경로|

특권 프로그램은 강력한 권한을 가지기 때문에, **코드에 버그가 하나라도 있으면** 공격자가 그 권한을 악용해 보호된 자원에 접근할 수 있다.
