## 0) 한 문장으로 먼저 잡기

- **VPC**: AWS 안에 만드는 “내 전용 네트워크(가상 공간)”
    
- **Subnet**: 그 네트워크를 “구역(동네) 단위로 나눈 것”
    
- **Public/Private**: “인터넷이 직접 연결되냐/안되냐” 차이
    

---

## 1) 왜 VPC가 필요해?

AWS에서 EC2(서버), RDS(DB) 같은 걸 만들면 결국 **네트워크 안에 배치**해야 합니다.

현실로 비유하면:

- 인터넷 = 도로/외부 세상
    
- 서버/DB = 건물 안의 방
    
- 네트워크 = 건물 단지
    

AWS는 “아무 데나” 서버를 놓는 게 아니라, **네가 만든 네트워크 공간(VPC) 안에** 서버를 놓도록 설계되어 있습니다.

즉, VPC는:

- 내 서버들이 쓸 **IP 주소 범위**
    
- 외부/내부 통신 방법(라우팅)
    
- 접근 규칙(보안)  
    을 내가 정하는 **기본 판(땅)** 입니다.
    

---

## 2) VPC의 핵심: “IP 주소 범위(CIDR)”를 정한다

VPC를 만들 때 제일 먼저 하는 게 이겁니다.

예:

- VPC CIDR: `10.0.0.0/16`
    

이게 뜻하는 건:

- 이 VPC 안에서 쓸 수 있는 IP가 **10.0.0.0 ~ 10.0.255.255** 범위라는 의미입니다.
    
- “우리 단지에서는 이 주소들만 쓸 거야” 라고 정하는 겁니다.
    

왜 중요하냐면:

- 서버는 각각 IP를 가져야 통신이 됩니다.
    
- 주소 범위를 먼저 정해야 “서버를 몇 대까지 둘지”도 결정하기 쉽습니다.
    

현실 비유:

- VPC CIDR = “아파트 단지의 주소 체계(동/호수 범위)를 정함”
    

---

## 3) Subnet은 왜 나누는 거야?

VPC가 단지 전체라면, Subnet은 단지 안의 구역(동네)입니다.

왜 나누냐?

1. **보안 분리** (인터넷에 노출되는 구역 vs 내부 구역)
    
2. **장애 분산** (AZ라는 “물리적으로 다른 데이터센터”에 나눠 배치)
    
3. **네트워크 정책 분리** (구역별 라우팅/방화벽 다르게)
    

예시로 VPC를 이렇게 쪼갤 수 있어요:

- VPC: `10.0.0.0/16`
    
    - Subnet A: `10.0.1.0/24`
        
    - Subnet B: `10.0.2.0/24`
        
    - Subnet C: `10.0.3.0/24`
        
    - Subnet D: `10.0.4.0/24`
        

여기서 `/24`는 “한 서브넷에 IP를 대략 256개 정도” 쓸 수 있는 크기라고 생각하면 됩니다.

---

## 4) Public Subnet vs Private Subnet (가장 중요)

처음에 제일 헷갈리는 포인트인데, 결론부터 말하면:

### Public Subnet

- **인터넷과 직접 연결되는 구역**
    
- 여기에는 보통:
    
    - 웹 서버(EC2)
        
    - 로드밸런서(ALB)
        
    - Bastion(접속용 서버)  
        를 둡니다.
        

### Private Subnet

- **인터넷과 직접 연결되지 않는 구역**
    
- 여기에는 보통:
    
    - DB(RDS)
        
    - 내부 API 서버
        
    - 캐시/큐 같은 내부 인프라  
        를 둡니다.
        

현실 비유:

- Public Subnet = “정문이 있는 구역(외부 사람이 들어올 수 있음)”
    
- Private Subnet = “관리동/기계실 같은 내부 구역(외부에 노출하면 위험)”
    

---

## 5) Public/Private를 가르는 진짜 기준은 “라우팅”

많이들 “서브넷 만들 때 public 체크하는 건가?”라고 생각하는데,  
**진짜로는 라우팅 테이블(Route Table)이 결정**합니다.

### Public Subnet이 되려면

- 그 서브넷의 라우팅 테이블에
    
    - `0.0.0.0/0 → Internet Gateway(IGW)`  
        라는 규칙이 있어야 합니다.
        

뜻:

- “모든 외부(인터넷)로 가는 길을 IGW로 내보내라”
    

### Private Subnet은

- 위 규칙이 없거나,
    
- 인터넷으로 나갈 때도 **NAT Gateway를 통해서만** 나가게 만들면 됩니다.
    

---

## 6) Internet Gateway(IGW)와 NAT Gateway를 아주 쉽게

### IGW (Internet Gateway)

- VPC가 인터넷과 연결되는 “문”
    
- Public Subnet에서 “밖에서 들어오고/밖으로 나갈 수 있음”
    

### NAT Gateway

- Private Subnet 인스턴스가 **밖으로 나가기만** 하게 해주는 장치
    
- 인터넷에서 **직접 들어오는 건 막고**
    
- 업데이트/패키지 설치 같은 **아웃바운드만 허용**
    

예:

- Private Subnet의 DB 서버가 보안 업데이트 하려고 인터넷으로 나가야 함
    
- 하지만 외부에서 DB로 들어오게 하면 위험
    
- 그래서 NAT를 통해 “나가는 것만” 허용
    

---

## 7) “서버(EC2) 하나 만든다”를 예시로 전체 흐름 연결

### 웹 서비스 기본 구조

1. **VPC 생성** (예: `10.0.0.0/16`)
    
2. **Public Subnet 2개** (AZ를 나눠 고가용성)
    
3. **Private Subnet 2개**
    
4. **IGW 생성 + VPC 연결**
    
5. **Public Subnet 라우팅 테이블에 IGW 연결**
    
6. (선택) Private Subnet용 **NAT Gateway 생성**
    
7. **EC2 웹서버는 Public Subnet**
    
8. **RDS는 Private Subnet**
    

이렇게 하면:

- 사용자는 인터넷으로 웹서버에 접속 가능
    
- DB는 외부에서 직접 접근 불가능 (웹서버만 접근)
    

---

## 8) 최종 요약 (암기용)

- **VPC**: 내 AWS 전용 네트워크(주소/정책의 큰 틀)
    
- **Subnet**: VPC를 나눈 구역(리소스를 배치하는 단위)
    
- **Public Subnet**: 라우팅이 IGW로 열려있어서 인터넷 직접 가능
    
- **Private Subnet**: 인터넷 직접 불가, 필요하면 NAT로 “나가기만” 가능
