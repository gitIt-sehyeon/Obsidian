# ✅ 캐스캐이드리스(Cascadeless) 스케줄 — 핵심 정리

## 📌 정의

**Cascadeless 스케줄**이란,  
어떤 트랜잭션이 **커밋되지 않은(uncommitted) 데이터**를  
다른 트랜잭션이 **읽지 못하게 하는 스케줄**이다.

즉,

> **T_j는 T_i가 commit한 데이터만 읽을 수 있음**  
> → 커밋되지 않은 값을 읽는 것을 완전히 금지

이것을 통해 **cascade(연쇄 롤백)를 방지**한다.

---

# 📌 캐스캐이딩 롤백(Cascading Rollback) 방지 조건

T_j가 T_i가 write한 데이터 Q를 읽는 경우:

`T_i.commit  <  T_j.read(Q)`

즉,  
**읽기(read)는 반드시 쓰기(write)의 commit 이후에만 가능**해야 한다.

🔸 읽기(read)를 허용하기 위한 조건  
→ **T_i의 commit이 먼저 와야 함**

---

# 📌 왜 중요한가?

트랜잭션 T_i가 실패하면 rollback이 일어나는데,  
만약 T_j가 T_i의 “아직 commit되지 않은 데이터”를 읽고 있었다면?

→ T_j도 rollback  
→ T_j를 읽은 T_k도 rollback  
→ …  
→ 연속된 롤백 **(cascading rollback)** 발생

Cascadeless 스케줄은 이 문제를 **구조적으로 발생하지 않도록 보장**한다.

---

# 📌 회복 가능성(Recoverability)과의 관계

|개념|조건|
|---|---|
|**Recoverable 스케줄**|T_j가 T_i의 값을 읽었다면, **T_j는 T_i commit 이후에 commit해야 함**|
|**Cascadeless 스케줄**|T_j가 T_i의 값을 읽으려면, **T_i commit 이후에 read해야 함**|

### 관계 정리

- **Cascadeless ⇒ Recoverable** (항상 참)
    
- Recoverable이지만 Cascadeless는 아닐 수 있음 (read는 가능한데 commit 조건만 지키는 경우)
    

즉,  
**Cascadeless는 Recoverable보다 더 강한 조건**을 요구한다.

---

# 📌 중요한 이유

1. **연쇄 롤백 발생 방지**  
    → rollback 오버헤드 감소  
    → 시스템 안정성 증가
    
2. **트랜잭션 간의 “dirty read” 제거**  
    → DB 일관성 증가
    
3. **복구 비용 감소**  
    → 관리가 훨씬 쉽고 안정적인 트랜잭션 환경 제공
    

그래서 대부분의 DBMS는  
**Cascadeless 또는 Strict 스케줄(strict 2PL)**  
쏠림 정책을 사용한다.

---

# ✔ 요약 (한 문장)

> **Cascadeless 스케줄 = T_j가 T_i의 커밋된 데이터만 읽게 하여, cascade rollback을 완전히 방지하는 강한 형태의 recoverable 스케줄**
