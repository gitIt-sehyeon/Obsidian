# ✅ View Serializability — 핵심 요약

**View Serializability(뷰 직렬 가능성)** 은  
동시 실행된 스케줄이 **어떤 직렬 스케줄과 “같은 결과를 낸다면”**  
그 스케줄을 올바른 것으로 인정하는 기준이다.

즉,

> **동시 실행되더라도 "논리적으로" 직렬 실행과 동일하다면 OK**

---

# 🔷 1. 정의 (Definition)

스케줄 S가  
어떤 직렬 스케줄 S′와 **뷰 동등(view equivalent)** 하다면,  
스케줄 S는 **뷰 직렬 가능(view serializable)** 하다.

---

# 🔷 2. 뷰 동등성 조건 (View Equivalence Conditions)

스케줄 S와 S′(직렬 스케줄)이 **같은 트랜잭션 집합**을 가진다고 할 때,  
모든 데이터 항목 Q에 대해 아래 3가지 조건이 같으면  
두 스케줄은 “뷰 동등”하다.

---

## ① Initial Read (초기 값 읽기)

S에서 어떤 트랜잭션 Tᵢ가  
Q의 **초기 값**을 읽은 경우,  
S′에서도 Tᵢ는 Q의 **초기 값**을 읽어야 한다.

> 즉, “초기에 누구 값 읽는지”가 동일해야 한다.

---

## ② Intermediate Read (중간 값 읽기)

S에서 트랜잭션 Tᵢ가  
Q의 값을 읽었는데 그 값이 Tⱼ의 write(Q)에서 나온 값이라면,

S′에서도 **Tᵢ는 Tⱼ가 쓴 값**을 읽어야 한다.

> “누가 쓴 값을 읽었는지”가 동일해야 한다.

---

## ③ Final Write (최종 쓰기)

S에서 Q에 대해 **마지막으로 write(Q)** 한 트랜잭션이 Tₖ라면,  
S′에서도 Tₖ이 Q에 대한 **최종 write**를 해야 한다.

> “최종 결과를 누가 결정했는지”가 같아야 한다.

---

# 🔷 3. Conflict Serializability와의 관계

✔ 모든 Conflict-serializable 스케줄 ⊆ View-serializable 스케줄  
즉,

> **Conflict Serializability → View Serializability**  
> (항상 참)

✖ 하지만 그 반대는 아님.

### 이유: **Blind Write(블라인드 쓰기)** 때문

- 데이터를 읽지 않고 바로 write(Q) 하는 경우
    
- 충돌 기반 검사에서는 직렬 가능성이 없지만
    
- 뷰 관점에서는 최종 결과가 같다면 허용될 수 있음
    

---

# 🔷 4. 테스트의 어려움

뷰 직렬 가능성 판별 → **NP-complete 문제**

→ 일반적으로 효율적으로 검사하기 어렵다  
→ 실제 DBMS는 이런 복잡한 검사 사용 X

✔ 대신 Conflict Serializability(판별 쉬움)를 기준으로 동시성 제어를 한다.


---

# 🎯 View Serializability 판정 절차 (초간단 3단계)

스케줄 S가 있을 때  
S가 어떤 직렬 스케줄 S′과 **뷰 동등(view equivalent)** 한지 확인하면 된다.

뷰 동등을 판정하는 3가지 조건은 다음과 같다:

---

# ✅ Step 1: Initial Read (초기값 읽기) 체크

스케줄 S에서  
트랜잭션 Tᵢ가 **Q의 초기값(initial value)** 을 읽었다면,

→ 직렬 스케줄에서도 Tᵢ는 **초기값을 읽어야 한다.**

### 👉 체크 방법

스케줄을 보고  
`Tᵢ.read(Q)` 가 해당 Q의 **첫 write보다 앞에 있는지** 보면 된다.

예:

`T1: read(A)   ← 첫 write(A)보다 앞이면 "초기값 읽기" T2: write(A)`

→ T1은 A의 초기값을 읽음  
→ 직렬 스케줄에서도 T1은 초기값을 읽어야 함.

---

# ✅ Step 2: Intermediate Read (중간값 읽기) 체크

스케줄 S에서  
Tᵢ가 Q를 읽을 때, 그 값이 **어떤 Tⱼ의 write(Q)** 에서 나왔다면:

→ 직렬 스케줄에서도 “Tᵢ는 Tⱼ가 쓴 Q의 값"을 읽어야 한다.

### 👉 체크 방법

모든 `read(Q)` 를 보며  
바로 이전에 Q를 write한 트랜잭션이 누구인지 확인하면 된다.

예:

`T1: write(A) T2: read(A)   ← 여기서는 T1이 write한 값을 읽음`

→ 직렬 스케줄에서도  
`T1` → `T2` 순서가 되어야 함  
(그래야 T2가 T1의 값을 읽을 수 있음)

---

# ✅ Step 3: Final Write (최종 쓰기) 체크

스케줄 S에서  
**Q를 마지막으로 write한 트랜잭션이 Tₖ** 라면

→ 직렬 스케줄에서도 Tₖ이 Q에 대해 마지막 write를 해야 한다.

### 👉 체크 방법

`write(Q)` 중 **가장 마지막 write**를 찾는다.

예:

`T1: write(A) T2: write(A)   ← 마지막 write(A)`

→ 최종 write(A)는 T2  
→ 직렬 스케줄에서도 T2이 마지막 write가 되어야 한다.

---

# 🎉 View Serializability 판정 방법 정리

1. **초기 read 관계** 맞추기
    
2. **각 read가 누구 write를 읽었는지(read-from)** 맞추기
    
3. **마지막 write 관계** 맞추기
    

→ 이 3개 규칙을 모두 만족할 수 있도록  
→ 트랜잭션을 Tₓ → Tᵧ → … 순으로 한 줄로 세울 수 있으면  
→ **view serializable**

못 세우면  
→ **view serializable 아님**

이게 전부이다.

---

# 🔥 그럼 너가 헷갈려하던 예시로 바로 적용해보자

스케줄 S:

`T1: write(A) T2: write(B) T2: write(A)`

## Step 1: 초기값 읽기

읽기 연산이 없으므로 pass.

## Step 2: 중간 read 관계

읽기가 없으므로 pass.

## Step 3: 최종 write

- A의 최종 write = T2
    
- B의 최종 write = T2
    

→ 직렬 스케줄에서도 T2가 마지막에 있어야 한다.

따라서 가능한 직렬 스케줄:

`T1 → T2`

직렬 스케줄 T1 → T2와 비교:

`T1: write(A) T2: write(B) T2: write(A)`

완전히 동일한 결과  
→ **view serializable ✔**

즉, 계산 끝.

---

# 🔥 이제 “안 되는 예시”도 하나 해보자

스케줄 S:

`T1: write(A) T2: read(A) T2: write(A) T1: read(A)`

### Step 1: 초기 read

없음.

### Step 2: 중간 read

- `T2.read(A)` → T1.write(A)에서 읽음 → T1 → T2 순서 필요
    
- `T1.read(A)` → T2.write(A)에서 읽으려면 T2 → T1 순서 필요
    

→ **T1 → T2 and T2 → T1** 둘 다 필요  
→ 순서를 만들면 cycle 발생  
→ 직렬 스케줄 불가능  
→ **view serializable X**

이게 바로 view serializable이 안 되는 이유.

---

# 🔥 핵심은 이 3가지 체크만 하면 된다

|체크|무엇을 보나?|예|
|---|---|---|
|초기 읽기|첫 write보다 앞에 있는 read|initial read|
|중간 읽기|read가 어디서 값을 받았는가?|왜곡된 read-from 관계가 있으면 불가|
|최종 write|마지막 write의 주인 누구?|직렬 스케줄에서도 동일해야 함|

---

# ⭐ 마무리 요약

> **뷰 직렬성 = read-from 관계 + 초기값 읽기 + 최종 write를 직렬 스케줄로 복원 가능한가를 보는 것**
