# 1. 정상적인 트랜잭션 처리 중 취해지는 조치 (Actions taken during normal transaction processing)

목표: 실패 발생 시 복구에 필요한 충분한 정보를 확보하는 것입니다.
내용:
데이터베이스 시스템은 트랜잭션이 수행하는 모든 변경 사항과 관련된 정보를 기록합니다.
주로 Log라는 특별한 파일을 Stable Storage에 유지하며, 이 로그에는 트랜잭션의 시작, 데이터 항목의 변경 전후 값, 트랜잭션의 커밋(<Ti commit>) 또는 중단(<Ti abort>)과 같은 정보가 Log Record 형태로 기록됩니다.
이 정보는 트랜잭션의 Atomicity와 Durability를 보장하기 위해 필수적입니다. 예를 들어, Immediate Database Modification 방식에서는 데이터가 실제 디스크에 쓰여지기 전에 반드시 로그 레코드를 Stable Storage에 먼저 기록하여, 시스템 크래시 시에도 데이터 변경 사항을 복구할 수 있도록 합니다.


목적 달성 기여: 이러한 사전 조치를 통해 시스템은 나중에 실패가 발생하더라도 어떤 트랜잭션이 무엇을 변경했는지, 그리고 그 변경이 완료되었는지 여부를 정확히 파악할 수 있는 근거를 마련합니다.


# 2. 실패 후 데이터베이스 내용을 복구하기 위해 취해지는 조치 (Actions taken after a failure)

목표: 데이터베이스 내용을 Atomicity, 일관성(Consistent State), Durability를 보장하는 상태로 복구하는 것입니다.
내용:
시스템 Failure (예: System Crash 또는 Disk Failure)가 발생하면, 시스템은 이전에 기록된 로그 정보를 활용하여 복구 절차를 시작합니다.
Undo 연산: 실패 시점에 아직 커밋되지 않은 트랜잭션(<Ti start>만 있고 <Ti commit> 또는 <Ti abort>가 없는 트랜잭션)이 데이터베이스에 미친 모든 변경 사항을 되돌려(rollback) 데이터베이스를 해당 트랜잭션이 시작하기 전의 상태로 복원합니다. 이는 Atomicity를 보장합니다.
Redo 연산: 커밋되었지만 변경 사항이 아직 디스크에 완전히 반영되지 않았을 수 있는 트랜잭션(<Ti commit>이 있는 트랜잭션)의 변경 사항을 다시 적용하여(forward application) Durability를 보장합니다.
Checkpoint 메커니즘을 사용하여 복구 시 스캔해야 할 로그의 양을 줄여 복구 시간을 단축할 수 있습니다.


목적 달성 기여: 이 과정을 통해 데이터베이스는 실패 이전의 마지막 Consistent State로 복원되며, 커밋된 모든 트랜잭션의 변경 사항이 유지되고, 커밋되지 않은 트랜잭션의 변경 사항은 모두 취소됩니다.
