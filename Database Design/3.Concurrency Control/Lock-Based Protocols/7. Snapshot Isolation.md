# ✅ 스냅샷 격리(Snapshot Isolation, SI) 

스냅샷 격리(SI)는 **트랜잭션 시작 시점의 DB 스냅샷**을 기반으로 읽기 작업을 수행하는 동시성 제어 방식이다.  
각 트랜잭션은 **자신만의 고정된 스냅샷**을 보며 실행되기 때문에 읽기 충돌이 거의 없고 성능이 높다.

하지만 **직렬화 가능(Serializable)을 항상 보장하지 않는다**는 치명적인 한계가 있다.

---

# 📌 1. 스냅샷 격리 동작 원리

- 트랜잭션 시작 시점의 **일관된 스냅샷**을 읽는다
    
- 다른 트랜잭션의 **커밋되지 않은 write는 보지 않는다**
    
- 트랜잭션이 write를 할 때는 **동일 데이터를 수정하려는 다른 트랜잭션과 write-write 충돌**이 발생하면  
    → 나중 트랜잭션이 abort 됨
    

즉,

> **읽기는 스냅샷에서, 쓰기는 최신 데이터에 대해 충돌 검사**

---

# 📌 2. SI가 직렬화 불가능을 만드는 이유

각 트랜잭션은 **서로 다른 시점의 데이터**를 보면서 의사결정을 한다.

따라서 여러 트랜잭션이 “서로 영향을 안 보고 서로 다른 값 기반으로 판단”하는 상황이 발생한다.

→ 이로 인해 **직렬 실행에서는 절대 발생할 수 없는 결과(Anomalies)** 가 나타날 수 있음.

---

# 📌 3. 대표적인 이상 현상 — Write Skew (쓰기 비대칭)

> **스냅샷 격리에서 가장 유명한 anomaly**

## ✔ 발생 조건

- 두 트랜잭션이 서로 다른 row를 수정하지만
    
- 수정 여부 판단은 서로의 값을 기반으로 함
    
- 그러나 SI에서는 서로 **이전 버전**을 읽기 때문에
    
- 두 트랜잭션 모두 조건을 만족한다고 생각하고 동시에 commit 함  
    → 결과가 **무결성 제약을 위반**하게 됨
    

## ✔ 예시

초기 상태  
A = 3  
B = 17

### T1

- A(3)을 읽고 → B를 수정해야 한다고 판단
    
- 하지만 T2가 이미 B를 바꿨는지 모름
    

### T2

- B(17)을 읽고 → A를 수정해야 한다고 판단
    
- T1이 이미 A를 바꿨는지 모름
    

두 트랜잭션 모두 커밋되면  
→ **직렬 실행에서는 절대 나올 수 없는 비일관적 결과** 발생  
→ 이것이 _Write Skew_

---

# 📌 4. SI가 항상 위험한가?

아님. 실무에서 **대부분 정상 작동**한다.

예)

- TPC-C 같은 유명 벤치마크도 SI에서 잘 돌아감
    
- write-write 충돌이 있는 데이터(예: 재고 수량)는 SI가 자동으로 abort 시켜 줌
    

문제는 특별한 조건(서로 다른 row를 수정하지만, 서로의 값을 기반으로 결정)이 있는 경우.

---

# 📌 5. SI의 구조적 문제 — 읽기-쓰기 충돌을 추적하지 않음

SI는

- **쓰기-쓰기 충돌(write-write)**만 추적
    
- **읽기-쓰기(read-write)** 충돌은 무시
    

즉,

- T1이 읽은 데이터(A)가
    
- T2에 의해 나중에 바뀌어도  
    → **T1이 이를 모른 채 commit할 수 있음**
    

이게 바로 직렬화 불가능성의 핵심 원인.

---

# 📌 6. Serializable Snapshot Isolation (SSI) — 해결책

SSI는 기존 SI에 **추가 검증 로직**을 추가하여 완전한 직렬화 가능성을 보장한다.

### ✔ SSI가 하는 일

- 읽기-쓰기 종속성(read-write dependency)을 추적
    
- dependency graph를 구성
    
- **사이클이 생길 것 같은 트랜잭션을 abort**
    

→ 결과적으로 **직렬 스케줄과 동일한 효과** 보장

### ✔ 구현된 DB

- PostgreSQL 9.1+ 에서 제공
    
- 인덱스 잠금(index locking)을 사용해 **팬텀 읽기**까지 해결
    

---

# 📌 7. 주의할 점 — “Serializable”이라고 해서 진짜 직렬화가 아닐 수도 있다

일부 DBMS는

- 사용자가 `SERIALIZABLE`을 설정해도
    
- 내부적으로는 **스냅샷 격리 기반의 구현**을 사용한다 (예. 옛날 Oracle, PostgreSQL 9.1 이전)
    

따라서 DBMS가 제공하는 실제 격리 수준이 무엇인지 확인이 필요함.

---

# ✅ 요약 한 줄

> **스냅샷 격리는 빠르고 실용적이지만, 읽기-쓰기 종속성을 추적하지 않아 Write Skew 등 직렬화 불가능한 결과가 발생할 수 있다. 이를 해결하려면 SSI가 필요하다.**
