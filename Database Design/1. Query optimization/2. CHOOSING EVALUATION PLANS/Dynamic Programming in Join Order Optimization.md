# 1️⃣ 왜 피보나치 형태가 등장하는가? (가장 중요한 부분)

조인 순서를 찾는 문제는 다음과 같이 재귀적으로 정의된다.

`bestPlan(S) = min over all S1 ⊂ S of                 cost( bestPlan(S1) ⋈ bestPlan(S − S1) )`

즉 S라는 릴레이션 집합을

- 두 집합 S1, S2 = S−S1 로 쪼갠 뒤
    
- 각각의 best plan을 다시 재귀적으로 계산
    

→ 합쳐서 비용을 비교

이 구조가 **피보나치 수열의 재귀 정의와 동일하다.**

---

# 2️⃣ 피보나치와 Join 계획 재귀의 구조가 왜 같을까?

피보나치 수열의 정의는:

`F(n) = F(n-1) + F(n-2)`

이때 **F(n-1)과 F(n-2)는 서로 겹치는 부분 재귀를 많이 포함한다.**

예:

- F(5) = F(4) + F(3)
    
- F(4) = F(3) + F(2)
    
- F(3) = F(2) + F(1)
    

여기서 F(3), F(2) 같은 계산이 **계속 반복됨**

→ **중복 계산 폭발**

---

# 3️⃣ Join Order 문제에서도 같은 일이 벌어진다

예를 들어 S = {A,B,C,D} 라고 해보자.

가능한 분할:

`(A) ⋈ (BCD)   (B) ⋈ (ACD)   (C) ⋈ (ABD)   (D) ⋈ (ABC)`

그리고 BCD의 bestPlan(BCD)을 찾으려면 다시:

`(B) ⋈ (CD)   (C) ⋈ (BD)   (D) ⋈ (BC)`

여기서 bestPlan(CD), bestPlan(BD), bestPlan(BC), bestPlan(CD) 등  
**같은 부분문제가 반복적으로 등장한다.**

→ **Fibonacci형 중복 재귀와 동일한 구조**

그래서 만약 DP 안 쓰면:

### ❌ 시간 복잡도 = O(2^n)

→ 릴레이션 10개만 있어도 1024개 조합  
→ 실제 조인 계획 후보는 수백/수천 개

---

# 4️⃣ 그래서 슬라이드가 말하는 “기저 사례(base case)” 등장

기저:

`bestPlan({Ri}) = 단일 릴레이션 접근 비용`

이걸 기반으로 재귀적으로 합치는 거지.

# 5️⃣ DP 방식으로 해결하는 이유

DP는 “이미 계산한 부분해를 저장(memotize)”한다.

그래서

`bestPlan(S)`

이 한 번 계산되면,  
다음에 또 S를 분해하거나 사용할 때 바로 꺼내 쓴다.

→ **피보나치의 중복 재귀 폭발을 막아준다**

그래서 최종 계산량은 O(n·2^n) 수준으로 줄어든다.

이는 DBMS가 실제로 사용하는 System R의 기법이다.

# 6️⃣ 쉽게 비유하면?

조인 순서 최적화 문제는:

- n개의 릴레이션을 가지고
    
- 가능한 모든 “이진 트리 형태의 조인 계획”을 고려한다.
    

이때 가능한 이진 트리 수는 **카탈란 수(Catalan number)**인데  
카탈란 수 자체가 피보나치와 비슷한 재귀 폭발 구조를 가진다.

즉:

`조인 순서 조합 개수 ≈ 피보나치 또는 카탈란 수 정도로 폭발함`

그래서 DP가 필수다.

# ⭐ 완전 요약

1. 조인 순서를 찾을 때 집합 S를 모든 부분집합으로 나누어  
    bestPlan(S1) + bestPlan(S−S1)를 재귀적으로 구하면
    
2. 피보나치처럼 **같은 부분집합이 계속 재계산됨**
    
3. 그래서 DP를 이용해  
    “부분집합 S의 bestPlan은 메모리에 저장하고 다시 사용”한다.
    
4. 이게 바로 **피보나치 DP와 동일한 패턴을 가진다.**
